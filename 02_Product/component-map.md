# Component Map

## Layout & Grid
Source: `app/styles/tokens.css`, `app/styles/grid.css`. Preview/vet at `app/frame.html`.

**Spacing scale** (also drives type line-height): 0, 4, 8, 16, 24, 32, 40, 48, 56, 64, 72. 4px is the only fine-adjustment step; everything above it moves in 8s.

**Grid:** 4 columns mobile, 8 tablet, 12 desktop (Material's standard layout-grid split — these three counts share clean factors, so half/quarter spans divide evenly everywhere; thirds only divide evenly at 12, so treat thirds as desktop-only).
- Mobile (< 600px): 4 columns, margin 16px, gutter 16px
- Tablet (600–1023px): 8 columns, margin 48px, gutter 16px
- Desktop (≥ 1024px): 12 columns, margin 72px, gutter 24px, content capped at 960px max-width (centers on larger screens)

Margins got a real bump at tablet and desktop (were 24px/32px) and max-width came down from 1200px — the page read close to edge-to-edge in practice, "like 10 columns" by feel even though the underlying grid was still technically 12 at desktop. `--grid-columns` itself wasn't touched (still 4/8/12) — changing that would break the "half always means half" contract `.col-half`/`.col-quarter`/`.col-third` depend on. The narrower, more-framed feel comes entirely from `--grid-margin`/`--grid-max-width` instead.

Because column count itself changes per breakpoint, spans are semantic classes, not fixed numbers: `.col-full`, `.col-half`, `.col-quarter`, `.col-third` (desktop-only, falls back to full width below 1024px). Each carries its own correct span at every breakpoint — e.g. `.col-half` is 2/4 → 4/8 → 6/12.

**Base reset** (`grid.css`, `button, input`): `appearance: none`/`-webkit-appearance: none` plus `font: inherit`/`color: inherit` — a real, previously-missing gap (nothing in the app had ever reset native button chrome), worth keeping regardless, but it turned out not to be the actual fix for "Add a show" reading off-center; see the Add show card entry below for the real cause and fix, confirmed by rendering the button headless and reading actual `getBoundingClientRect()`/text-ink positions rather than guessing from a screenshot.

**Type scale:** six sizes now, two faces. Big Shoulders Display is headline-only (900 weight, pinned explicitly) — it read as too loud on buttons/dates/avatars/labels, so data and body both moved to Public Sans, told apart by size/case/tracking rather than a typeface swap. Controls (12px) turned out too small once they were carrying every button in the app, not just dates/labels — split into its own size. Line-heights pulled from the spacing scale so type rhythm and layout rhythm are the same rhythm.
| Size | Line-height | Font | Use |
|---|---|---|---|
| 12 | 16 | Public Sans, uppercase + tracked (data) | timestamps, counts, meta labels |
| 14 | 16 | Public Sans, uppercase + tracked, semibold (control) | buttons, links, tappable controls |
| 16 | 24 | Public Sans (body) | default reading size |
| 20 | 24 | Public Sans, semibold (body) | card titles |
| 24 | 32 | Big Shoulders Display, 900 | section headings |
| 40 | 48 | Big Shoulders Display, 900 | hero numbers, page title |

**Color:** dark now, deliberately (an earlier dark-page attempt was reverted as a misread of an ambiguous request; this is a distinct, specific ask). `--color-bg` is charcoal (`#211f1a`) — the page itself, not a chip color living on a light page. `--color-surface` (`#2b2924`) is the card + drawer fill — one step lighter than the page, staying in the dark register (the opposite move from the old light-mode "cards lighter toward white"). `--color-surface-text` (`#ebe8e1`, warm paper) is text/icons on `--color-surface`; `--color-text` is the same paper value at the page level. Flipping the page to dark broke the old "dark chip on a light page" trick for filled/active elements (buttons, the calendar weekday header — the calendar was later cut entirely in favor of the Herd Picks/My Shows tabs) — a charcoal chip on an already-charcoal page is invisible — so those now use two new tokens instead: `--color-chip-bg` (`#ebe8e1`, paper) / `--color-chip-text` (`#211f1a`, charcoal), the same duotone logic just inverted polarity. `--color-text-inverse` stays pinned to white regardless of any of this — it's specifically "white text for a colored/dark fill" (avatar dots, the overlap badge), independent of which way the page itself goes. `--color-border` moved from solid charcoal to a translucent paper hairline (`rgba(235, 232, 225, 0.18)`) — a solid charcoal border would vanish on a charcoal page. Pink accent (`#f3596e`) is now unified across the app — overlap marker, wordmark "Gig," and the header avatar's hover state all share this one value (`--color-logo-pink` is just an alias for `--color-accent` now, not a separate value). This relaxes the earlier "pink means overlap, nowhere else" rule on purpose — see `brand-brief.md` for the full history of why. "Herd" keeps its own dedicated `--color-logo-green` (`#8dc63f`), still pinned to the London Calling / Elvis Presley cover homage — see Header nav below. No glow anywhere in the app; a glow pass on the wordmark's green half was tried and cut.

**Measure rule:** body copy targets 60–75 characters per line. On desktop, full-width (12 columns) runs too long — `.col-half` lands closer to the right measure. Use `.prose` (max-width: 65ch) alongside it for any real paragraph so the cap holds regardless of column width.

**Discipline:** every color, spacing, and type value in a component should reference a token from `tokens.css` (`var(--...)`). If a value doesn't exist as a token and needs to be reusable, add it to `tokens.css` first rather than hardcoding — flag it here when that happens so the scale stays intentional, not sprawling.

**Token audit — main screen spacing pass.** A direct request to clean up main-screen spacing and double-check token usage turned up a real, previously-invisible bug and a cluster of un-tokenized values:
- **`<p>` margin leak.** `.header-tagline` and `.footer-copyright` are both `<p>` tags with no `margin-bottom` (or, for the footer one, no margin at all) set explicitly — meaning each was quietly inheriting the browser's own default `<p>` margin (~16px, unrelated to any token), stacking on top of the header's own `--space-24` padding and `.show-list`'s `--space-32` top padding to make the gap under the tagline noticeably bigger than the design actually specifies. Found by rendering the header headless and reading the *computed* margin directly (`getComputedStyle(...).marginBottom` returned `16px`, not `0`) rather than guessing from a screenshot. Both now zero this out explicitly.
- **Duplicate rgba() literals, now `color-mix()` tokens.** `rgba(33, 31, 26, 0.45)` (the flat scrim, used identically by both the drawer and modal overlays) and four separate `rgba(235, 232, 225, …)` hover/active tints were all hand-typed decimal RGB re-derivations of colors that already had hex tokens (`--color-bg`, `--color-text`) — a second, unlinked source of truth for the same color that could drift out of sync silently. Replaced with `--color-scrim`, `--tint-hover`, `--tint-active`, `--tint-active-strong` in `tokens.css`, each built with `color-mix(in srgb, var(--color-bg-or-text) N%, transparent)` so they derive from the existing hex tokens instead of duplicating them. Also collapsed two near-identical hover opacities (0.06 and 0.08, used in different components for what was functionally the same "subtle hover" state) down to one shared value.
- **Off-scale magic numbers moved onto the scale or given a named token.** `.show-list-empty-icon`'s `56px` now reads `var(--space-56)` (already on the spacing scale — just wasn't being referenced). `.group-switch-item-count`'s `margin-top: 2px` — finer than the spacing scale's own "4px is the only fine-adjustment step" rule — became `var(--space-4)`. The wordmark's deliberately off-scale `30px` (documented as intentional — a step above `--text-head-size` but under `--text-display-size`) is now at least a named token, `--text-wordmark-size`, instead of a bare number sitting in `components.css` with no token backing at all.
- **Left alone, deliberately:** `.name-gate-box`'s `max-width: 400px` and `.modal-box`'s `max-width: 360px` — one-off content-width constraints, not part of the `--space-*` rhythm's contract (similar in kind to `--grid-max-width` itself being a standalone hardcoded value with its own token, not a multiple of the spacing scale).

**Fields — filled, not outlined.** Every text input in the app (`.form-row input` — name gate, Add Show's manual form, venue search) switched from a `1px solid var(--color-border)` outline on a background matching the page (`--color-bg`) to a real fill: `--color-input-bg`, a new token, one shade darker than `--color-bg` (`color-mix(in srgb, var(--color-bg) 80%, black)`). Worth naming: every other fill token in the palette goes *lighter* than `--color-bg` (`--color-surface` for cards, `--color-chip-bg` for active/filled buttons) — this is the one deliberate exception, chosen so a field reads as a recessed slot cut into the page rather than a raised surface sitting on top of it, which is what a lighter fill would have implied. Border dropped to `1px solid transparent` at rest (kept in the box model so nothing shifts on focus) — the fill itself is the field's boundary now; the existing accent focus ring stays a real outline, since "you're typing here" is a different signal from the field's resting shape. Padding also grew from `var(--space-8)` to `var(--space-8) var(--space-16)` — a bare `--space-8` all around read cramped once the field had real visual weight instead of just a thin outline.

**Icons — Lucide (lucide.dev), adopted as the app's standard iconset per explicit direction, starting with the share feature below.** Loaded from a pinned CDN build (`https://unpkg.com/lucide@1.29.0/dist/umd/lucide.min.js` — pinned per Lucide's own docs, not `@latest`, so an upstream release can't silently rename/change a glyph out from under the app), same external-CDN pattern the app already used for Supabase. Usage: plain `<i data-lucide="name"></i>` placeholders in the markup, swapped for real inline SVG by `lucide.createIcons()` at runtime. Two call sites, because `createIcons()` only replaces elements that exist in the DOM the moment it runs: a single top-level call (right before `init()` in the inline script) covers every icon already in the static HTML at load (`.drawer-close-btn`, `.modal-close-btn`, `.share-group-btn`); a second, scoped call (`lucide.createIcons({ root: drawerGroupList })`) sits inside `renderGroupSwitcher()`, re-run every time that list rebuilds, since each render wipes and regenerates its own `data-lucide` placeholders. `--icon-size` (`tokens.css`, 20px) is the one shared size for every icon-only control's SVG — button *boxes* still vary (`--space-40` for standalone circular controls, `--space-32` for the tighter in-row share button) but the glyph itself stays one consistent size everywhere, the same "box sizes the tap target, not the glyph" convention the old text-glyph buttons already used. Migrated so far: the drawer's ✕ and the people-modal's ✕ (both now `x`), plus every share affordance (`share`, flashing to `check` on successful copy — see `flashShareSuccess()`). Deliberately **not** migrated yet: the Add Show `+`/rotate-to-`×` toggle (its 45°-rotation trick is a plain CSS `transform` on the existing glyph span and works identically with an SVG child, but it's untouched for now to avoid risk to an already-tuned mechanism without a specific reason to touch it) and the empty-state guitar silhouette (hand-built from filled shapes; Lucide has no equivalent figurative icon). Revisit both if/when there's a reason to, rather than migrating for its own sake.

## Components
- **Name gate** (`app/index.html`, logic in `app/scripts/identity.js`) — the whole "onboarding" surface, and deliberately not a splash page: when a browser has no `otr_person_id` cookie, the header and main content stay hidden and a centered box shows instead (`.name-gate-center`, flex-centered both axes, `.name-gate-box` capped at 400px — same treatment for every step below). Replaces the old `window.prompt()`.
  - **Two paths, decided once at load** by whether `?g=<slug>` is in the URL (`inviteSlug`/`hasInviteSlug`, captured before `handleGroupJoinFromUrl` strips it). A cold-start visitor (no link) gets the generic tagline ("Line up shows with your pals") and a second field in the same form — Group name — so person + first group get created together in one submit, followed by a share screen right after: two full-width actions ("Copy invite link", "+ Add first show") front and center, a quiet "Skip to your group" link below for anyone who wants past both. "+ Add first show" reveals the real app with the Add Show panel already open, so this screen gives way to the normal list the moment a show actually gets added.
  - **Invite-link message — names the actual group, as a second line.** First pass overwrote the generic tagline entirely on the invite path — cut after direct feedback, since it left the brand tagline missing and the two ideas ("here's the app" / "here's what you're joining") reading as one line with no room to breathe. Now `#name-gate-invite-message` is a separate `<p>`, hidden by default, sitting *under* `#name-gate-tagline` (which stays "Line up shows with your pals." on every path, invite or not) with real margin between the two. `init()` runs a separate, early `getGroupBySlug(inviteSlug)` (purely for display, before the person has even entered a name — distinct from the `getGroupBySlug` call inside `handleGroupJoinFromUrl`, which only runs after submit and actually joins) and sets its text to `You've been invited to join "{Group Name}" to track shows together. Add your name and jump in.`, then shows it. Stays hidden if the slug doesn't resolve (stale/bad link) rather than claiming an invite that isn't real. Deliberately doesn't name *who* invited them — the link is one per group, not one per sender, so there's no reliably correct person to credit; a wrong name would read worse than no name (see `01_Strategy/decisions.md`, 2026-08-06).
  - **Joining a group via invite link**: `OTR.getGroupBySlug` + `OTR.joinGroup` add the person to that group and land them in it — works both for a brand-new person (right after the name gate) and a returning one opening a friend's link for a group they're not in yet. The URL param gets cleaned up after processing so a refresh doesn't reprocess it. This is the join mechanism, full stop — no separate "invite code" concept, the slug just lives in a shareable link instead of something typed in, since sharing happens over text/iMessage where a tappable link beats a typed code.
  - **Slug format — readable name, not a hash.** `groups.slug` used to be `schema.sql`'s own default, a random 12-byte hex string (`098aea86c5eb9dc6461b166f`) — private-by-obscurity, but it made every invite link and the URL bar itself look broken. `OTR.createGroup` now slugifies the group's actual name client-side (lowercase, non-alphanumerics collapsed to single hyphens — "The Usual Suspects!!" → `the-usual-suspects`) and passes it explicitly on insert, overriding that DB default. A same-name collision retries with `-2`, `-3`, ... on the table's unique-constraint violation (Postgres `23505`) rather than failing outright — a few groups sharing a name across different friend circles is expected at this scale. Existing groups keep their old hex slugs (no retroactive rename — would break already-shared links); only groups created from here forward get readable ones. Trades away some of the earlier "unguessable slug" privacy stance — see `01_Strategy/decisions.md`, 2026-08-06, for the reasoning and the accepted risk (someone who guesses a common group name and knows to try it could self-join, since `joinGroup` has no approval step).
  - **Restyle — one centered column, filled fields.** The wordmark, tagline, input fields, and Continue button are a centered block. Field labels (`.name-gate-box .form-row label`) went through a center-aligned pass and back — centered read fine while there was only ever one field in view, but with two stacked ("What's your name?" / "Group name") a centered question sitting dead over its own answer field read odd; labels are left-aligned again now, same as every other form in the app, while the fields/button themselves stay full-width. Inputs switched from outlined to filled — see **Fields — filled, not outlined** below; this is app-wide, not scoped to the name gate, since Add Show's manual form and the name gate share the same `.form-row input` class.

## Data Flow
Real data end to end now. `renderShowList(groupId)` fetches shows for the current group, then all responses for those shows in one query (`getResponsesForShows`), grouped client-side by `show_id`. Clicking a response button writes to Supabase and re-fetches the whole list rather than patching state locally — simplest thing that works at this scale, revisit if the group's show count grows enough that a full re-fetch per click feels slow.
